# Communities Part 3: the chat (brief)

Written on 3 Nov 2026 for the build of Part 3; not started yet. Parts 1 and 2 are described in docs/COMMUNITIES_PLAN.md and docs/HANDOVER.md. Browser tests for the earlier parts are kept in tools/browser-tests/ (see its README).

PART C3: the chat itself for 1,000-person community chats: live updates, history paging, mute, and role-coloured nicknames. The database side (realtime broadcast trigger, realtime.messages policy, thread_mutes + set_thread_mute, keyset index, community branches in the chat functions, thread_members with nickname/role/membership) and the shared helpers (packages/shared/src/communities.ts and chats.ts: fetchMessagesPage, fetchMessagesAfter, roleColour, roleTag, setThreadMute, muteUntil, communityRoster) are already in the working tree from part C1; read supabase/migrations/20261202000000_communities.sql and those files first, and docs/COMMUNITIES_PLAN.md ("Chat at 1,000+ members"). Part C2 built the community screens (app/c/[slug]/...); its Chat tab has a placeholder component (look under components/community/) for you to replace with the embedded main chat.

Current chat screen: apps/mobile/src/app/chats/[id].tsx (about 615 lines): it polls every 4 to 16 seconds (lastAt / lastActivity / AppState / useIsFocused), renders all loaded messages in a ScrollView, loads the last 100, jumps to the pinned message using measured positions, and has media uploads, event shares, pins, report/block, leave/rejoin, and a group menu. Keep every existing feature working for every chat kind (event, social, direct, community).

What to build:
1. Extract the chat body into a reusable component (e.g. components/chat/chat-view.tsx) used by app/chats/[id].tsx and by the community home's Chat tab (replace C2's placeholder: the main chat embedded under the banner and tabs, with a "Open full screen" button to /chats/<id>). Keep app/chats/[id].tsx's behaviour and testIDs (existing browser tests rely on them).
2. History: open with the newest 50 (fetchMessagesPage), "Load older messages" at the top (and automatically when scrolled to the top) loading 50 more by keyset (created_at, id) with no duplicates or gaps, keeping the scroll position steady when older messages are prepended. The pinned-message jump must still work when the pinned message is older than what's loaded (load pages until it's found, capped, or fall back to the existing fetchMessagesFrom approach). A full virtualised list is deferred to next week (keep ScrollView if switching risks the pinned jump; say which you chose and why).
3. Live updates via Supabase Realtime, for EVERY chat kind: while the chat is open and the app is in the foreground, subscribe to supabase.channel(`thread:${id}`, { config: { private: true } }).on('broadcast', { event: 'message' }, ...). The payload is only { id, op } ('insert' or 'delete'); on insert fetch new messages with fetchMessagesAfter(last seen created_at,id) (never trust payload content; this also catches up anything missed and handles bursts by coalescing: one fetch in flight at a time, re-run if another broadcast arrived meanwhile); on delete refetch that message (fetchMessage) to show it as deleted. Make sure the realtime connection uses the logged-in user's access token (supabase-js normally does this; check supabase.realtime.setAuth is called after login/refresh if needed, e.g. on onAuthStateChange). Remove the channel (supabase.removeChannel) when leaving the chat, when the screen loses focus, and when the app goes to the background; on returning to the foreground or reconnecting, resubscribe and catch up with fetchMessagesAfter (paged; never skip messages even if more than 100 arrived). Fallback polling: while the channel is SUBSCRIBED poll only every 60 seconds as a safety net; while it is not (CHANNEL_ERROR, TIMED_OUT, CLOSED, or still connecting) poll every 4 to 8 seconds like today, so the chat keeps working if Realtime is unavailable or the project's connection limit (200 concurrent clients on the free plan) is reached. Never open more than one channel per chat; log channel status changes in development only. Put the subscription logic in a small hook (e.g. lib/use-live-thread.ts) with the coalescing/catch-up decisions in a pure, unit-tested function in packages/shared.
   Note: there is no local Realtime server, so browser tests can't receive broadcasts: make the hook degrade to polling when the channel never reaches SUBSCRIBED (that's what the local tests will exercise), and test the pure logic with unit tests. The owner will test live delivery on the staging Supabase project afterwards.
4. Mute: in the chat's header menu, for every chat kind: "Mute notifications" with 1 hour, 8 hours, 1 week, Always; "Unmute" when muted (show "Muted until 18:30" / "Muted until Tue 10 Nov" / "Muted" in the menu and a small muted icon in the header). Uses setThreadMute; the Chats tab shows the muted icon (C2 may have done the row part; make it consistent). Unread counts still show.
5. Names in community chats: each message shows the sender's community nickname (not their profile name) in the role colour for the current light/dark scheme (roleColour with the community's settings.role_colours, precedence admin > committee > member > non-member) plus a small tag ("Admin", "Committee", "Member"; none for non-members) next to the name. Load the roster once per community with react-query (communityRoster or thread_members; cache, refresh every few minutes and when an unknown sender appears). People who left show their nickname greyed. Your own messages keep the existing "me" styling. Tapping a name opens their profile as today. Other chat kinds look exactly as before. Check readability of the colours on the actual message bubble/background colours in both modes (the plan's colours were checked against the app backgrounds; if any name colour sits on a bubble with contrast below 4.5:1, put the name above the bubble instead of inside it).
6. Members screen (app/chats/members.tsx) for community chats: show nickname, role tag and colour; admin actions there should route to the community's Manage screen instead of the per-chat admin tools (thread_admins don't apply to community chats).
7. Performance: no per-message network calls (media URLs and shared events are already batched; keep it so); memoise message rows; don't re-render the whole list on every poll; with 1,000 messages loaded after paging, scrolling and typing must stay smooth on a mid-range phone (measure render counts in a test if feasible).

Tests: unit tests for the pure realtime/catch-up/coalescing logic, paging merge (no duplicates, correct order, keyset boundaries with equal created_at), mute labels, and name colour/tag selection; browser tests (tools/browser-tests, following existing ones; seed communities/users in the test via sql()): community chat shows nicknames with role tags and colours (assert computed colour in light and dark), "Load older" pages through 120+ seeded messages without gaps, the embedded chat on the community page, mute menu sets and clears (assert thread_mutes row), polling fallback delivers a message sent by another user within 10 seconds when Realtime is unavailable, existing chat tests (chats, chats-tabs, society-chat, report-event and any chat-related ones) still pass. Light and dark screenshots of a community chat at phone width saved for the owner to look at.
